# Session prompts (วางสั้นๆ จากโทรศัพท์ได้)

ไฟล์นี้เก็บ prompt ที่ใช้เปิด session ของ agent เพื่อให้สั่งงานได้ด้วยประโยคสั้นๆ แทนการวางข้อความยาว
กฎของโปรเจกต์อยู่ที่ [`CLAUDE.md`](../../CLAUDE.md) เสมอ — ไฟล์นี้ไม่ซ้ำกฎ ถ้าขัดกันให้ยึด `CLAUDE.md`

## วิธีใช้
พิมพ์ประโยคเดียวในข้อความแรกของ session แล้วบอกหัวข้อที่ต้องการ ตัวอย่าง:

> ทำตาม `docs/workflow/SESSION-PROMPTS.md` หัวข้อ **B** กับงาน **UAM-SHL-01** — ผมอนุญาตให้ push branch `feature/UAM-SHL-01-shell` และเปิด PR ตามที่ไฟล์กำหนด

> ทำตาม `docs/workflow/SESSION-PROMPTS.md` หัวข้อ **A** — งาน: UAM-SHL-01, UAM-FND-03, UAM-FND-04 — ผมอนุญาตให้ push branch `<type>/<CODE>-<slug>` ของแต่ละงานตามที่ไฟล์กำหนด

ข้อความ "ผมอนุญาตให้ push branch …" ในประโยคสั่งเป็น**คำอนุญาตอย่างชัดแจ้ง**ที่ session บนคลาวด์ต้องการ (บาง session ถูกกำหนดให้ push ได้เฉพาะ branch ของตัวเอง) ถ้าไม่ใส่ agent อาจ push ได้เฉพาะ branch ที่ระบบกำหนด ซึ่งดู `CLAUDE.md` §5 ข้อยกเว้น

---

## 0. กฎกลางของทุกหัวข้อ (agent ต้องทำตามเสมอ)
1. อ่าน `CLAUDE.md` ทั้งไฟล์ก่อน โดยเฉพาะ: clean-room (ห้ามเปิดโค้ดเก่า), ห้ามแก้หลังบ้าน, ห้าม merge PR ตัวเอง, รายงานผลตามจริง
2. branch ชื่อ `<type>/<CODE>-<slug>` แตกจาก `origin/develop` ล่าสุด หนึ่งงานต่อหนึ่ง branch และหนึ่ง PR ห้ามรวมงาน ห้ามซ้อน PR (CI รันเฉพาะ PR ที่ base เป็น `develop`)
3. push ได้เฉพาะ branch ของงานที่ระบุในคำสั่งของผู้ใช้ ห้าม push เข้า `develop`/`main` ห้าม force push ถ้า push ถูกปฏิเสธ ให้หยุดและบอกผู้ใช้ (อย่าหาทางอ้อม)
4. **push ทุก commit ทันที** — container บนคลาวด์ถูกเก็บคืนเมื่อไม่ได้ใช้งาน งานที่ไม่ push จะหาย
5. ก่อนเปิด PR ต้องรันจริง: `npm run test:ci`, `npm run build`, และ `npm run check:no-demo` (หลัง build production) ถ้าไม่ผ่านให้แก้ ห้ามข้าม/แก้ test ให้ผ่านแบบหลอก
6. PR ใช้ `.github/PULL_REQUEST_TEMPLATE.md` ครบทุกช่อง base = `develop` ใส่ `Closes #<issue>` (ปิด issue อัตโนมัติตอน merge เพราะ default branch คือ `develop`)
7. ทำเฉพาะขอบเขตของ item (`docs/backlog/items/<CODE>.md`) สิ่งที่เจอเพิ่มให้เสนอเปิด issue ใหม่ ไม่ทำเอง ห้ามเพิ่ม dependency โดยไม่ผ่าน Senior
8. ใช้ skill ตาม `CLAUDE.md` §3: `uam-pick-backlog` ก่อนเริ่ม, `karpathy-guidelines` ทุกงานที่เขียนโค้ด, งาน frontend ใช้ `frontend-design` หรือ `superdesign` ภายใต้กรอบสเปก แล้วทำตาม `uam-frontend-implement`, `uam-open-pr` ตอนส่ง
9. รายงานให้สั้นอ่านบนโทรศัพท์ได้: ตารางหนึ่งตาราง + ลิงก์ PR + สิ่งที่ยังไม่ได้ตรวจ อย่ารายงานว่าสำเร็จถ้ายังไม่ได้รันจริง

---

## A. ทำหลายงานต่อเนื่อง เปิด PR ค้างไว้ แล้วผู้ใช้ merge ทีเดียว
ใช้เมื่อ: งานหลายตัวที่ไม่ขึ้นต่อกัน และอยากกด merge รอบเดียว

ผู้ใช้ระบุรายการงานในประโยคสั่ง (เช่น UAM-SHL-01, UAM-FND-03, UAM-FND-04) ทำตามนี้:
1. ตรวจ `docs/backlog/status.json`: ทำเฉพาะงานที่ dependency เป็น `done` ครบ **ตั้งแต่ก่อนเริ่ม** งานที่ขึ้นต่อ PR ที่ยังไม่ merge ให้ข้ามและบอกผู้ใช้
2. ทำทีละงานตามขั้นใน **B** เมื่อเปิด PR เสร็จให้กลับไป `origin/develop` ล่าสุดแล้วเริ่มงานถัดไปได้เลย โดย**ไม่รอ merge**
3. ไฟล์ร่วม (`app.config.ts`, `app.routes.ts`, `app.html`) แก้เท่าที่จำเป็น และจดไว้ว่า PR ไหนแตะบรรทัดไหน
4. รายงานครั้งเดียวตอนจบ (หรือเมื่อถูกบล็อก): ตาราง งาน / ลิงก์ PR / ผล `test:ci` `build` `check:no-demo` ที่รันจริง / ไฟล์ร่วมที่แตะ / สิ่งที่ยังไม่ได้ตรวจ แล้วเสนอ**ลำดับ merge ที่เสี่ยง conflict น้อยที่สุด** และบอกว่า PR ไหนน่าจะต้อง "Update branch" หลังตัวก่อนหน้า merge
5. จำกัดไม่เกิน 3 งานต่อ session เพื่อไม่ให้ session ยาวเกินไป

## B. ทำงานเดียว
1. `git fetch` แล้วแตก branch จาก `origin/develop`
2. อ่าน `docs/backlog/items/<CODE>.md` และ issue ตรวจ dependency (`status.json`) ถ้าไม่ครบ ให้หยุดและบอกผู้ใช้
3. เขียน **test ก่อน** แล้ว implement เฉพาะขอบเขตของ item
4. รันตามกฎกลางข้อ 5 แล้วเปิด PR (งาน UI แนบ screenshot desktop 1440 และ phone 390 ด้วย Chromium/Playwright ที่ติดตั้งไว้)
5. รายงาน: ลิงก์ PR + ผลทดสอบจริง + ความเสี่ยง

## C. รีวิว PR (session แยกจากผู้เขียน)
ใช้เมื่อ: มี PR เปิดค้างและอยากให้ตรวจก่อนกด merge — ผู้รีวิวต้องไม่ใช่ session ที่เขียน PR นั้น

ผู้ใช้ระบุเลข PR (หรือ "ทุก PR ที่เปิดอยู่") ทำตาม skill `uam-review-pr`:
1. ดู diff, CI, ขอบเขตเทียบ item, กฎ clean-room, ฟิลด์/payload เทียบ `src/testing/fixtures`, test ที่เขียนก่อนจริงหรือไม่
2. รัน `npm ci && npm run test:ci && npm run build` บน branch ของ PR เพื่อยืนยันผลเอง
3. คอมเมนต์ผลรีวิวลงใน PR (approve / request changes พร้อมเหตุผล) ลงท้ายด้วย footer "Generated by Claude Code" **ห้าม merge**
4. สรุปให้ผู้ใช้: PR ไหนพร้อม merge, PR ไหนต้องแก้, ลำดับ merge ที่แนะนำ

## D. Stand-up
ตาม skill `uam-daily-standup`: อ่านสถานะจริงจาก GitHub (PR/issue/label/CI) และ `status.json` แล้วสรุป เสร็จแล้ว / ค้างอะไร / ความเสี่ยง / ควรทำต่อ (เฉพาะงานที่ dependency ครบ) / คำถามที่รอตัดสินใจ ถ้าผู้ใช้สั่ง ให้เขียนเป็น `docs/reports/daily/<YYYY-MM-DD>.md` ผ่าน PR **ห้ามเริ่มงานใหม่เองจนกว่าผู้ใช้สั่ง** ข้อมูลที่อ่านไม่ได้ให้เขียนว่า "ตรวจไม่ได้" อย่าเดา

## E. รอบ QA ต่อ wave
ใช้เมื่อ: wave หนึ่ง merge ครบแล้ว ตาม skill `uam-qa-run`: ทดสอบตาม test case ใน `docs/testing/` กับ build `demo` (หรือ `https://client-new-uam.vercel.app/`) บันทึกผลจริงลง `docs/qa/results/` ผ่าน PR รายงานผ่าน/ไม่ผ่านพร้อม screenshot และเสนอ "ตีกลับ / เปิด issue ใหม่" ให้ผู้ใช้ตัดสิน — **ห้ามแก้โค้ดแอปเพื่อให้ test ผ่าน**

## F. งานเอกสาร backlog หลัง merge
ใช้เมื่อ: มีงาน merge แล้วและต้องซิงก์เอกสาร ตาม skill `uam-backlog-sync`: สร้าง `docs/backlog/status.json` จาก label ของ issue ด้วย `gh issue list --state all --limit 200 --json number,state,stateReason,labels | npm run gen:status` (ตรวจ label ไม่ตรงอย่างเดียว: ต่อท้าย `-- --check`; สคริปต์ `scripts/gen-status.mjs` ไม่แตะ network/token — ห้ามแก้ `status.json` ด้วยมือ), เปลี่ยน label `status:*` ของ issue ที่เกี่ยวข้องเป็น `status:qa`, ลงทะเบียนงานใหม่ใน `items/`, `BACKLOG.md`, `EXECUTION-PLAN.md`, `ISSUES.md`, `issue-map.json` ผ่าน PR (`docs/<slug>`)

## หมายเหตุ
- **ปิด issue อัตโนมัติ:** default branch ของ repo คือ `develop` แล้ว `Closes #<issue>` ใน PR จะปิด issue ตอน merge ส่วน label `status:*` และ `status.json` ยังต้องอัปเดตเอง (หัวข้อ F) จนกว่าจะมี automation
- **Vercel:** production domain build จาก `develop` ด้วย `build:demo` ส่วนลิงก์ preview ของแต่ละ PR ต้อง login Vercel (Standard Protection) ดู `docs/workflow/VERCEL-PREVIEW.md`
- **ถ้า session ไม่ยอม push branch ชื่อ `<type>/<CODE>-<slug>`:** ให้ทำตามข้อยกเว้นใน `CLAUDE.md` §5 (ใช้ branch ที่ระบบกำหนด ใส่ backlog code ใน PR/commit และต่อประวัติด้วย `git merge -s ours` ห้าม force push) และผู้ใช้ควรทำทีละ PR
