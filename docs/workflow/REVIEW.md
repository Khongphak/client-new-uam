# 🔍 ข้อดี–ข้อเสียของ workflow ปัจจุบัน (ไว้ใช้ปรับปรุง)

สถานะ: ออกแบบแล้วแต่ **ยังไม่เคยรันกับงานจริง** — ข้อสังเกตด้านล่างมาจากการวิเคราะห์ ไม่ใช่ผลวัด ควรทบทวนหลังจบ 1–2 story แรก

## ✅ ข้อดี
| ข้อ | เหตุผล |
|---|---|
| ตรวจสอบย้อนกลับได้ | ทุกงานผูก backlog code → branch → commit → PR → test case → ผล QA |
| กั้นความรับผิดชอบชัด | PM ไม่เขียนโค้ด, QA ไม่แก้โค้ดให้ผ่าน, Dev ไม่ merge → ลดการ "ตรวจงานตัวเอง" |
| Test ก่อนโค้ด | test case เป็น `.md` ก่อน implement, Dev ทำ TDD |
| ลดงานผิดทิศ | Senior กรอง backlog ก่อนจ่ายงาน, สเปกที่ยืนยันแล้วชนะเสมอ |
| Dependency/wave ชัด | ทำคู่ขนานได้เท่าที่ปลอดภัย |
| ขอบเขตแคบ | `karpathy-guidelines` + กฎ "ห้ามเกินขอบเขต" ลด diff บวม |
| ผู้ใช้คุมจุดเสี่ยง | `main`/deploy ต้องผู้ใช้อนุมัติ, ไม่มี schedule ที่ทำงานเองโดยไม่มีคนดู |
| ทุกอย่างเป็นไฟล์ใน repo | ย้าย/ต่อยอด/เปลี่ยน agent ได้ง่าย |

## ⚠️ ข้อเสีย / ความเสี่ยง และข้อเสนอแก้
| # | ปัญหา | ผลกระทบ | ข้อเสนอ |
|---|---|---|---|
| 1 | **ไม่มี branch protection ที่บังคับได้เลย (ทั้ง `main` และ `develop`)** — private repo บนแผนปัจจุบัน GitHub ไม่บังคับ ruleset →  กฎ "ห้าม push ตรง / CI ต้องเขียว / Senior ≠ ผู้เขียน" เป็นแค่ข้อตกลง | agent พลาดหรือข้ามกฎได้โดยไม่มีอะไรกั้น; develop อาจแดง | ทางเลือกถาวร: (ก) อัปเกรดแผน (GitHub แจ้งว่าต้อง Team org; ตรวจหน้า pricing ว่าแผนส่วนบุคคลพอไหม) (ข) ทำ repo เป็น public (ไม่แนะนำถ้ามีข้อมูลภายใน) (ค) อยู่กับข้อตกลง: ใส่ CI บน push `develop` (มีแล้ว) + กฎ "develop แดง = แก้/revert ก่อนทำอย่างอื่น"; ให้ QA/PM ตรวจ log `git log develop` เป็นระยะ; พิจารณา protect แบบเบา (บังคับแค่ CI, ไม่บังคับ review) เมื่อพร้อม |
| 2 | **ทุก agent ใช้ GitHub account เดียวกัน** → ใครเป็น "Senior ≠ ผู้เขียน" พิสูจน์ด้วยระบบไม่ได้ และ GitHub ไม่ให้ approve PR ตัวเอง | review เป็นแค่คอมเมนต์ ไม่ใช่ approval จริง; ช่องว่างความเชื่อถือ | ระบุ role ใน PR template (ทำแล้ว); ถ้าต้องการจริง: สร้าง GitHub App/bot account แยกสำหรับ Senior |
| 3 | **Review ด้วย LLM ตัวเดียวกัน/โมเดลคล้ายกัน** → อคติเดียวกันเห็นปัญหาซ้ำๆ ไม่ครบ | บั๊กหลุดแม้ผ่านรีวิว | ใช้ CI + contract test + QA เป็นตาข่ายหลัก; ให้คนสุ่มอ่าน PR สำคัญ (routing/guard/payload) |
| 4 | **คอขวดที่ Senior** (รีวิว+merge+จ่ายงาน) | งาน Junior ค้างรอ; dependency chain ยาว (critical path ~48 pts) | จำกัด WIP; แยก PR ให้เล็ก; Senior รีวิวก่อนทำงานตัวเอง |
| 5 | **ไม่มี pre-merge E2E/ภาพเทียบ artboard** — QA ทดสอบหลัง merge | บั๊กเข้า develop ก่อนถูกจับ → ต้อง revert/แก้ | เพิ่ม screenshot บังคับใน PR (ทำแล้ว); เพิ่ม visual regression หลังมี Phase 1; ถ้าถี่ ให้ QA ทดสอบบน PR preview ก่อน merge |
| 6 | **ข้อมูลใน backlog ยังไม่ถูกตรวจกับโค้ดจริง** ("Actual result" เขียนจากสเปก) และ test case เป็นสมมติฐาน (testid, flow) | Dev/QA เชื่อข้อมูลผิด | `uam-pick-backlog` ข้อ 4 ให้ยืนยันก่อนเริ่ม; PM แก้เอกสารเมื่อพบ |
| 7 | **สถานะซ้ำหลายที่** (label, `status.json`, EXECUTION-PLAN, รายงาน) | ข้อมูลไม่ตรงกัน | ให้ label ของ issue เป็นแหล่งจริง; `status.json` สร้างจาก issue (สคริปต์) ในอนาคต |
| 8 | **ไม่มีงานเปิด issue จริงยังเลย** + label ยังไม่ได้สร้าง | agent ติดตามสถานะไม่ได้ | PM เปิด issue 42 รายการ + สร้าง label เป็นงานแรก |
| 9 | **ไม่มี schedule** → PM ทำงานเมื่อผู้ใช้เรียกเท่านั้น | งานค้างถ้าผู้ใช้ไม่เปิด session | ยอมรับ (ตั้งใจ) — ผู้ใช้คุมจังหวะ; ถ้าต้องการ ค่อยทำ schedule ที่ผูก GitHub connector |
| 10 | **หลาย agent แก้ไฟล์กลางพร้อมกัน** (routing, styles, shared) | merge conflict | ทำ FND ให้เสร็จก่อนขนาน; รีเบสจาก develop ก่อนเปิด PR; Senior แก้ conflict |
| 11 | **ยังไม่มี deploy pipeline / environment** | "ผ่านก่อน deploy จริง" ยังตรวจไม่ได้ | ตัดสินใจเป้า deploy แล้วเพิ่มเป็น backlog (staging + smoke E2E) |
| 12 | **ต้นทุน/ความเร็ว**: แต่ละ story ผ่านหลาย agent + หลายรอบ | ช้าและเปลืองสำหรับงานเล็ก | ให้งานเล็กมาก (≤1 pt, เช่น ERR-01) รวม PR; ปรับ model ต่อบทบาท |
| 13 | **Skill `karpathy-guidelines` เป็นฉบับย่อที่เขียนเอง** ไม่ใช่ตัวจริง | ความเข้มงวดอาจต่างจากต้นฉบับ | ติดตั้งตัวจริงถ้ามี แล้วลบฉบับย่อ |

## 🎯 สิ่งที่ควรวัดหลังรัน 1–2 story
- เวลา/จำนวนรอบจาก `ready` → `done` · จำนวนรอบ request changes ต่อ PR · อัตรา QA ไม่ผ่านต่อ story · สัดส่วน "ตีกลับ" vs "issue ใหม่" · จำนวนครั้งที่ develop แดง · จำนวน PR ที่ Senior ต้องแก้ conflict
