# UAM-DSN-01 — Spec ปิดช่องว่างดีไซน์ (ร่างที่ 1, ข้อความล้วน)

สถานะ: **ร่างให้ผู้ใช้รีวิว** ยังไม่ใช่ดีไซน์ที่ยืนยัน (acceptance ของ #3 ต้องการให้ผู้ใช้ยืนยัน)
ครอบคลุมช่องว่างข้อ 1 ใน `README.md` หัวข้อ "ช่องว่างที่ยังเปิดอยู่": (A) phone ของหน้าสถานะ (B) error ของ drawer ใน System Setting (C) ชื่อซ้ำ 40301

หลักการ: ใช้คอมโพเนนต์เดิมใน `uam.css` เท่านั้น (`u-state`, `u-errpage`, `u-dialog*`, `u-toast`, `u-skel`, `u-errlist`) ไม่เพิ่มคอมโพเนนต์ใหม่ ยกเว้นที่ระบุว่า "ใหม่" ข้อความภาษาอังกฤษตามน้ำเสียงเดิม (สั้น บอกสิ่งที่ทำต่อได้ ไม่โทษผู้ใช้) breakpoint phone = ต่ำกว่า 768px ออกแบบที่ 390px

## A. Phone ของหน้าสถานะ

กติกากลางของ phone: ระยะขอบหน้า 16px (`--sp-4`); ปุ่มกดสูง 44px; ปุ่มหลักอยู่ล่างสุดและกว้างเต็ม; ไม่มี hover-only; ไม่มีแนวนอนเลื่อน

| หน้า | Phone (390px) |
|---|---|
| **404 / 403** (`u-errpage`) | topbar 56px (โลโก้ซ้าย; ไม่มี sidebar); เนื้อหาจัดกึ่งกลางแนวตั้ง: ไอคอนใน `u-tile` 56px, `u-errpage__code` ("404" / "403"), หัวข้อ 22px (ลดจาก 28px), ย่อหน้า 15px กว้างสูงสุด 100% ปุ่มเรียงแนวตั้ง กว้างเต็ม: **Back to Home** (primary) แล้ว **Contact IT Support** (secondary/text) ข้อความเดิมตาม `ErrorPage` |
| **Dialog** (Session, Network, Server, Delete confirm, Delete fail) | ไม่ใช้ bottom sheet (คงโครงเดียวตามกติกา) กล่องกว้าง `calc(100vw - 32px)` สูงสุด 400px จัดกึ่งกลาง; ไอคอน + หัวข้อ + ย่อหน้า + แถวรายละเอียด (เช่น `Error 50001 · Database error`) ตัดบรรทัดได้ ไม่ตัดคำด้วย ellipsis; ปุ่ม**เรียงแนวตั้ง กว้างเต็ม** โดยปุ่มหลักอยู่บน ปุ่มรองอยู่ล่าง (กลับด้านจาก desktop ที่ชิดขวาแถวเดียว); ถ้าสูงเกินจอ เนื้อหาในกล่องเลื่อนได้ ปุ่มติดล่างกล่อง |
| **Home — loading** | การ์ดระบบ 1 คอลัมน์; `u-skel` 4 ใบ สูงเท่าการ์ดจริง; หัวหน้าหน้าเป็น skeleton แถวเดียว |
| **Home — empty** ("Data not found") | `u-state` ในพื้นที่เนื้อหา: ไอคอน, หัวข้อ, ย่อหน้า 1 บรรทัด ไม่มีปุ่มถ้าไม่มีทางแก้ที่ผู้ใช้ทำได้เอง |
| **Home — error** | `u-state` + ปุ่ม **Try again** กว้างเต็ม; ถ้าเป็นข้อผิดพลาดจากเซิร์ฟเวอร์ ให้บรรทัดรหัสเล็ก (`Error 50001`) ใต้ย่อหน้า |
| **ตาราง/รายการ — loading/empty/error** ("No Data Available") | แทนที่ตารางทั้งก้อนด้วย `u-state` ภายในการ์ด (ไม่แสดงหัวคอลัมน์ว่าง); แถบเครื่องมือ (ค้นหา, Filters) ยังอยู่ให้ล้างตัวกรองได้; empty ที่เกิดจากตัวกรองมีปุ่ม **Reset filters**; ท้ายตารางข้อความ "Showing…" ซ่อน paginator ย่อเหลือ prev/next + เลขหน้าปัจจุบัน |
| **Toast** (`u-toast`) | กว้าง `calc(100vw - 32px)` ชิดล่าง 16px (+ safe-area); หนึ่งใบต่อครั้ง ใบใหม่แทนใบเก่า; ปิดเองใน 6 วินาที เว้น error ที่ปิดเองไม่ได้ต้องมีปุ่มปิด 44px |

เกณฑ์ตรวจ: ที่ 390px ไม่มีแนวนอนเลื่อน, ปุ่มทุกตัวสูง ≥ 44px, ข้อความไม่ล้นกล่อง ที่ 320px ยังใช้ได้

## B. สถานะ error ของ drawer (System, Menu, System to System)

Drawer ใช้ร่วมกันทั้ง 3 ประเภท (ดู/เพิ่ม/แก้ไข) กว้าง 480px บน desktop; phone เต็มจอ (100vw) ไม่มีขอบมืด หัว drawer ติดบน ปุ่มบันทึกติดล่าง

| สถานการณ์ | พฤติกรรม |
|---|---|
| **โหลดข้อมูลของ View/Edit ไม่สำเร็จ** | เนื้อหา drawer เป็น `u-state` (หัวข้อ "Couldn’t load this record", ย่อหน้า "Check your connection and try again."), ปุ่ม **Try again** และ **Close**; ไม่แสดงฟอร์มเปล่า ปุ่ม Save ไม่แสดง |
| **โหลดอยู่** | `u-skel` แทนช่องฟอร์ม; ปุ่ม Save ปิดใช้งาน |
| **ตรวจฟอร์มไม่ผ่าน (ฝั่งไคลเอนต์)** | ข้อความ inline ใต้ช่อง (ตัวแดง 13px + ไอคอน); เช็กตอน blur และตอนกด Save; กด Save แล้วเลื่อนไปช่องแรกที่ผิดและโฟกัส; **ไม่**ปิดปุ่ม Save ล่วงหน้า (ต่างจาก Edit user ที่มีสรุปด้านบน) เพราะช่องที่ยังไม่แตะจะทำให้ปุ่มปิดโดยไม่รู้สาเหตุ |
| **บันทึกไม่สำเร็จ (เซิร์ฟเวอร์/เครือข่าย)** | แถบ error ที่**บนสุดของเนื้อหา drawer** (ไม่ใช่ toast เพราะ drawer บัง) ข้อความจากเซิร์ฟเวอร์ (`statusDescription`) + รหัส; ข้อมูลที่กรอกคงอยู่; ปุ่ม Save กลับมากดได้ ข้อผิดพลาดเครือข่ายและ 5xxxx ใช้ข้อความมาตรฐานของ dialog เดิม (Network / Server) ในแถบนี้ ไม่เด้ง dialog ซ้อน drawer |
| **Session หมดอายุระหว่างกรอก** | ใช้ `DlgSession` เดิม (เด้งทับ drawer); ข้อมูลฟอร์มไม่ถูกเก็บ (ระบุให้ชัดในข้อความ: "Your changes weren’t saved.") |
| **ปิด drawer ที่แก้ค้างอยู่** | ถามยืนยันด้วย dialog มาตรฐาน: "Discard changes?" / ปุ่ม **Keep editing** (primary) และ **Discard** — ใหม่เฉพาะข้อความ ใช้โครง dialog เดิม |
| **ลบจาก drawer ไม่ได้** | (ข้อเสนอเดิม) ใช้ `DlgDeleteFail` — **แต่ API ไม่มี endpoint ลบ** ดูหัวข้อ "ข้อค้นพบจากสัญญา API" ข้อ 1 จึงยังไม่ยืนยันว่าจะมีสถานการณ์นี้ |
| **ไม่มีสิทธิ์ (403) ระหว่างเปิด deep link** | เปิดหน้า 403 เต็มหน้า ไม่เปิด drawer |
| **deep link ไปเรคคอร์ดที่ไม่มี** | drawer เปิดแล้วแสดง `u-state` "This record doesn’t exist" + ปุ่ม **Close** (ไม่เปลี่ยนเป็น 404 เต็มหน้า เพราะยังอยู่ในหน้ารายการ) |

การเข้าถึง: แถบ error ใช้ `role="alert"`; โฟกัสย้ายเข้าช่องผิดแรก; ปิด drawer คืนโฟกัสให้ปุ่มที่เปิด; Esc ปิด (ผ่านขั้นตอนยืนยันถ้ามีการแก้)

## C. ชื่อซ้ำ 40301 (ALREADY_EXISTED)

**ข้อความ:** `This name is already in use. Choose a different name.` (ถ้า `statusDescription` ของเซิร์ฟเวอร์ระบุชื่อฟิลด์/ค่ามา ให้ใช้ข้อความมาตรฐานนี้ ไม่แสดงข้อความดิบ ยกเว้นเมื่อไม่รู้ว่าฟิลด์ใด ดู "คำถามเปิด" ข้อ 1)

**System / Menu / System-to-System drawer**
- ช่อง Name: กรอบแดง + ข้อความข้างต้นใต้ช่อง + ไอคอนเตือน; `aria-invalid="true"`, `aria-describedby` ชี้ข้อความ, ข้อความ `role="alert"`
- โฟกัสกลับช่อง Name ทันที; drawer ไม่ปิด; ข้อมูลอื่นคงเดิม; **ไม่**มีแถบ error ด้านบน (ซ้ำซ้อน)
- ข้อผิดพลาดหายเมื่อผู้ใช้แก้ค่าในช่อง; กด Save ซ้ำได้ทันที

**Role editor (3 ขั้น)** — ชื่ออยู่ขั้น 1 แต่ Save อยู่ขั้น 3
- เมื่อ Save ได้ 40301: ย้ายผู้ใช้**กลับขั้น 1** อัตโนมัติ, ขั้น 1 ใน `p-steps` มีจุดเตือนสีแดง, ช่อง Role name แสดง error แบบเดียวกับ drawer และโฟกัสที่ช่องนั้น
- ข้อมูลขั้น 2–3 (โครงเมนู, สิทธิ์) **ต้องไม่หาย**
- Phone: ข้อความเดียวกัน กว้างเต็มช่อง ตัดบรรทัดได้; `p-steps` เป็นแบบย่อ (เลขขั้น + ชื่อขั้นปัจจุบัน) จุดแดงบนเลขขั้นที่มีปัญหา

**Edit user:** ไม่เกี่ยวกับ 40301 (ใช้กติกา "ระบบซ้ำ" เดิมของ `EditDuplicate`)

## คำถามเปิดที่ต้องให้ผู้ใช้ตัดสิน

1. (ยังเปิด — ยืนยันแล้วว่าโค้ดเก่าไม่เคยจัดการ 40301 ต้องถาม backend) ฟิลด์ใดบ้างที่เซิร์ฟเวอร์ตรวจชื่อซ้ำแล้วตอบ 40301 (System name? Menu name? System-to-System? Role name? ทั้งหมด?) — ต้องยืนยันกับสัญญา API (#46) ถ้ายังไม่ทราบ ให้ถือว่า System name, Menu name, S2S name และ Role name
2. ปิด drawer ที่ยังไม่บันทึกต้องถามยืนยัน (ข้อเสนอ: ถาม) หรือปิดทันที?
3. Phone ของ dialog: ปุ่มเรียงแนวตั้ง (ข้อเสนอ) หรือคงแถวเดียวชิดขวาเหมือน desktop?
4. Drawer บน phone เต็มจอ (ข้อเสนอ) หรือเลื่อนขึ้นจากล่างเป็น sheet?

## ข้อค้นพบจากสัญญา API ที่กระทบดีไซน์ (เพิ่ม 2026-11-11, ดู `docs/api-contract/uam-api-contract.md` ภาคผนวก C)

1. **ไม่มี endpoint "ลบ" เลย** (ทุกเรคคอร์ดปิดด้วย `status: "Inactive"`) → dialog `DlgDeleteConfirm`/`DlgDeleteFail` และ #14 (ERR-04) ยังไม่มีงานที่ตรงกัน ต้องตัดสินใจ: (ก) ใช้เป็นการยืนยัน "Set to Inactive" (เปลี่ยนข้อความ ไม่ใช่ "Delete") หรือ (ข) ตัดออกจนกว่า backend จะมี endpoint ลบ ในตาราง B แถว "ลบจาก drawer" จึงยังเป็นข้อเสนอ ไม่ใช่พฤติกรรมที่ยืนยัน
2. **40301 มาได้ 2 ทาง:** HTTP 200 + `statusCode: "40301"` ในซอง (แอปเดิมแสดงข้อความตายตัว "Invalid input") หรือ HTTP 4xx ที่มี `message` (แอปเดิมเด้ง error modal ซ้อน) → แอปใหม่ต้องรองรับทั้งสองทางให้ออกมาเป็น **inline error ที่ช่องชื่ออย่างเดียว ไม่เด้ง modal ซ้อน**
3. **ทุกรหัสที่ไม่ใช่ 20000 เดิมออกมาเป็น "Invalid input" ข้อความเดียว** → ควรแยกอย่างน้อย: 40300 (พารามิเตอร์ไม่ถูกต้อง), 40301 (ชื่อซ้ำ, inline), 4xx/5xxxx (แถบ error ของ drawer ตามตาราง B), 422 `ModelState` (แสดงเป็นรายการ `u-errlist` ในแถบ error)
4. **Edit user: แถวระบบ+role ที่หา role ไม่เจอถูกตัดทิ้งเงียบๆ** แอปใหม่ต้องแสดง error ที่แถวนั้น (ตรงกับดีไซน์ `EditInvalid`) ไม่ปล่อยให้บันทึกโดยแถวหาย
5. **ช่อง Access/Refresh token time** ของ System drawer: ยังไม่ทราบหน่วย (นาที/วินาที) → ป้ายช่องต้องระบุหน่วยเมื่อได้คำตอบจาก backend; ฟอร์มเพิ่มระบบเดิมบังคับกรอกแต่ไม่ส่งค่า (บั๊กเดิม) → ต้องตัดสินว่าฟอร์ม Add ยังต้องมีสองช่องนี้ไหม
6. **เบอร์โทร** เป็นเบอร์ต่อภายในสั้นๆ ได้ (เช่น 4 หลัก) หรือว่าง → ห้าม validate เป็นเบอร์เต็ม
7. **ไอคอนเป็น SVG จากเซิร์ฟเวอร์** → ทุกที่ที่แสดงไอคอนต้องมีสถานะ fallback (ไอคอนโหลดไม่ได้/ไม่ผ่านการตรวจ) ใช้ไอคอน PrimeIcons ทดแทน

### คำถามเปิดเพิ่ม
5. Delete dialog: ใช้เป็น "Set to Inactive" หรือตัดออก? (ข้อ 1)
6. ฟอร์ม Add System ยังต้องมีช่อง token time ไหม และหน่วยคืออะไร? (ข้อ 5)

## คำตอบของคำถามเปิด (ร่าง — ผู้ใช้สั่งให้ Claude ตอบแทนเมื่อ 2026-11-11)

สถานะ: **ข้อเสนอที่เลือกให้แล้ว** ใช้เป็นค่าตั้งต้นเพื่อให้ #3 เดินต่อได้ ผู้ใช้ยังยืนยันดีไซน์ก่อนปิด #3 และเปลี่ยนข้อไหนก็ได้ (ตารางด้านบนไม่ต้องแก้ ยกเว้นที่ระบุ)

| # | คำถาม | คำตอบที่เลือก | เหตุผล |
|---|---|---|---|
| 1 | ฟิลด์ใดตอบ 40301 | **สมมติ:** System name, Menu screen name, Role name และ Username (ฟอร์ม User) แสดง inline error ที่ช่องชื่อ/ช่องนั้นเอง; S2S (คู่ source+target) แสดงข้อความที่ช่อง **Target system** ว่า `This system pair already exists.`; เก็บตารางจับคู่ "ฟอร์ม → ช่องที่แสดง error" ไว้ที่เดียวในโค้ดเพื่อแก้ง่าย **ต้องยืนยันกับ backend** (ถามอยู่ในสัญญา C.4) | ตอบจากโค้ดเก่าไม่ได้ (ไม่เคยจัดการ 40301); ตารางที่แก้ที่เดียวทำให้เปลี่ยนตามคำตอบจริงได้ถูก |
| 2 | ปิด drawer ที่ยังไม่บันทึก | **ถามยืนยัน เฉพาะเมื่อมีการแก้ค่า** (dirty) ด้วย dialog "Discard changes?" — **Keep editing** (primary) / **Discard**; ไม่ถามเมื่อไม่ได้แก้ | กันข้อมูลหายโดยไม่รบกวนตอนแค่ดู (View) |
| 3 | ปุ่ม dialog บน phone | **เรียงแนวตั้ง กว้างเต็ม** ปุ่มหลักอยู่บน | เป้าสัมผัส 44px ตามกติกา phone และกดพลาดน้อยกว่าสองปุ่มชิดกัน |
| 4 | Drawer บน phone | **เต็มจอ** (หัวติดบน ปุ่มบันทึกติดล่าง) ไม่ทำ bottom sheet | ฟอร์มยาว ไม่ต้องมี scroll ซ้อนสองชั้น และเลี่ยงปัญหาแป้นพิมพ์บัง |
| 5 | Delete dialog | **ใช้เป็นการยืนยัน "Set to Inactive"** (ข้อความ `Set this record to Inactive?`) ไม่ใช้คำว่า Delete เพราะ API ไม่มี endpoint ลบ; ถ้าเซิร์ฟเวอร์ปฏิเสธ ใช้ `DlgDeleteFail` เดิมด้วยข้อความ `Couldn’t change the status` + `message` ของเซิร์ฟเวอร์ | ตรงกับพฤติกรรมจริงของ API; ไม่ต้องออกแบบ dialog ใหม่; #14 (ERR-04) ปรับขอบเขตตามนี้ |
