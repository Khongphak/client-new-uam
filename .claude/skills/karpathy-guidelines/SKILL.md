> สรุปหลักการที่เป็นที่รู้จักจากข้อสังเกตของ Andrej Karpathy เรื่องข้อผิดพลาดของ LLM ตอนเขียนโค้ด ฉบับย่อสำหรับโปรเจกต์นี้ (ไม่ใช่ตัวต้นฉบับ) ถ้ามี skill ตัวจริงติดตั้งไว้ให้ใช้ควบคู่

1. **คิดก่อนเขียน** — ระบุข้อสมมติให้ชัด ถ้าไม่ชัดให้ถามหรือเสนอทางเลือกพร้อมข้อดีเสีย อย่าเลือกเงียบๆ; ถ้ามีวิธีง่ายกว่า ให้บอก
2. **เรียบง่ายก่อน** — โค้ดน้อยที่สุดที่แก้ปัญหา ไม่เพิ่มฟีเจอร์/abstraction/config ที่ไม่ได้ขอ ไม่รองรับกรณีที่เป็นไปไม่ได้; ถ้า 200 บรรทัดเขียนได้ 50 ให้เขียนใหม่
3. **แก้เฉพาะที่จำเป็น (surgical)** — แตะเฉพาะบรรทัดที่เกี่ยวกับงาน ไม่ "ปรับปรุง" โค้ดข้างเคียง ไม่ refactor ของที่ไม่พัง ตามสไตล์เดิม; เก็บกวาดเฉพาะส่วนที่การเปลี่ยนของเราทำให้ไม่ใช้
4. **ทำตามเป้าที่ตรวจสอบได้** — แปลงงานเป็นเกณฑ์ที่พิสูจน์ได้ (เขียน test ที่ fail ก่อน แล้วทำให้ผ่าน) วางแผนเป็นขั้นสั้นๆ พร้อมวิธีตรวจแต่ละขั้น แล้ววนจนผ่านจริง

เช็กก่อนส่ง: diff เล็กและตรงเรื่องไหม · ทุกบรรทัดที่เปลี่ยนโยงกลับไปถึงคำขอได้ไหม · มี test พิสูจน์พฤติกรรมไหม · รายงานผลตามจริงไหม
